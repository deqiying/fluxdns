## 1. 结论与源码差距

可编辑配置以不停机为目标：先准备并应用程序级候选，再持久化其原始配置表达。磁盘外部变化只生成待处理状态，不自动进入 reload。这里的“应用”是正式 owner 和请求接入已经切换，不是仅完成 parse/prepare。

| 源码 | 已有能力 | 本次必须改变 |
| --- | --- | --- |
| [app.rs](../../backend/src/app.rs) `ConfigFileWatcher`、`wait_for_ctrl_c_with_reload` 调用 | 连续两次稳定 fingerprint 后调用 `reload_service_from_path`；失败 retry | watcher 改为仅上报，文件读取有界且移出服务控制循环的同步 I/O |
| [ConfigStore](../../backend/src/config/store.rs)、[source_edit](../../backend/src/config/source_edit.rs) | 首用户源文件定向编辑、锁、fingerprint、双文件 journal | 扩展活动源表达、通用候选/状态；不能直接套用原“先文件后认证”的事务 |
| [service.rs](../../backend/src/service.rs) `reload_prepared` | BindPlan 相同则复用，否则全量 bind；CAS 后再 spawn/reconcile task | 差量复用 socket；处理 CAS 成功后 task 注册仍可能失败的窗口 |
| [RuntimeCoordinator](../../backend/src/runtime/coordinator.rs) | 活动快照、revision、mutation gate、旧请求 drain | 复用此权威，不另建 WebUI Runtime；补足提交成功定义 |
| [service.rs](../../backend/src/service.rs) `process_owned_reload_change` | database、logs、部分 webui、resolve_log 变化被拒绝 | 日志和详情开关改为可控热切换；启动级字段保留明确限制 |
| [observability.rs](../../backend/src/observability.rs) | 已有 reloadable filter/layer 与共享输出；app 在 logs 开启时才创建 writer | 复用 handle，设计始终存在的进程 owner 及 off/on 生命周期，不重复安装 subscriber |

2026-09-07 P0 已落实 revision、操作结果、配置读/变更和外部差异的内部 DTO/生成类型，详见 [Management 契约事实](../implementation/backend/management.md#p0-v2-契约)。追加授权的 P1 已落实 BC-02 活动源、定向候选、双文件只读观测和操作仲裁内部入口，详见[配置参考](../implementation/configuration.md#p1-活动源与候选内部底座2026-09-07)。正式控制命令、先应用后持久化、仅提示 watcher 和恢复仍留 BC-03/29/30/31；内部观测方法不等于 app watcher 已改变。不能因为已有 `reload_prepared` 或状态机成功回报就宣称实际 listener/owner 已完成切换或补偿。

## 2. 配置状态与权威

在现有 ConfigStore/Runtime 所有权内保留以下状态，不添加并行的配置数据库：

| 状态 | 用途 |
| --- | --- |
| `active_source` | 本进程当前活动配置的原始 DTO/可编辑语法树，保留相对路径、SecretRef、继承、显式缺省和允许的注释 |
| `active_revision` | 管理写入的活动配置版本；与一次请求捕获的 RuntimeRevision 明确关联，不混用资源刷新 epoch |
| `persisted_revision` | 已完成全部受管文件同步的活动版本；未持久化时可落后 |
| `observed_file_revision` | 源文件与派生副本的组合观测 token，覆盖 fingerprint 及缺失/不可读状态，防止任一文件在预览后再次变化 |
| `operation_id` / 同步状态 | 有界记录一次操作的准备、应用、持久化及结果；HTTP 丢失后查询，不能自动重放 |

operation_id 由客户端在发送前固定，并由服务端在有界窗口内关联命令摘要和结果；同 ID 不允许提交不同内容。记录已过期时明确返回结果未知，再回读活动版本/资源判断，不把找不到操作当作未执行。

配置 GET 来自 `active_source` 和活动 owner 状态。外部文件只是候选输入，不能直接成为表单默认值。`ResolvedConfig` 用于程序运行，不用于逆向生成写回数据；运行状态中的计数、健康、缓存条目也不能写入配置。

活动配置不是把外部文件和运行值混合出来的第三份真相。每次成功应用只更新一个活动版本和对应 owner；持久化同步的是同一版本，不按最新磁盘内容重新构建另一个候选。

源与 `<work.path>/config.yaml` 派生副本为同一路径时去重。不同路径继续按受管双文件处理；副本只用于一致持久化，不接受其外部内容作为第二输入源。

启动时先处理未完成 journal；没有待恢复事务时，以用户指定的源文件为输入，严格校验/prepare 成功后建立活动源。因此用户停机后修改启动配置可在下次启动采用，不继续沿用“运行中仅提示”的限制。已确认属于本实例的派生副本可重新同步，需调整当前 loader 的不同内容 no-replace 冲突路径；未知文件、符号链接/重解析点及错误目标仍拒绝覆盖。不能把任意文件认成派生副本。

## 3. 正常 WebUI 保存

```text
鉴权/Origin/严格 DTO
 -> 捕获 active_revision + observed_file_revision + originalName
 -> active_source 上定向修改字段和引用
 -> strict parse/validate/resolve + prepare 资源/owner/socket
 -> 准备受限临时文件和 PREPARED journal（不替换正式配置）
 -> 控制面串行提交，再检查两个 revision
 -> 切换运行对象及请求接入，确认 owner 可服务
 -> 持久化 COMMIT_DECIDED 标记
 -> 替换源文件与派生副本，校验并同步目录
 -> 更新 persisted_revision、自写 fingerprint、操作结果
```

### 3.1 应用边界

1. Management 通过有界控制命令交给持有 `DnsService` 的服务控制循环，不能在 handler 直接复制一套 supervisor 或只换 coordinator。
2. prepare 阶段可加载资源、预打开日志/文件、预绑定新增入口；使用现有 deadline，不能占用 DNS 请求锁等待网络/磁盘。
3. 应用与资源刷新/其他配置命令遵循统一串行提交边界；耗时准备在边界外，提交前再验证版本。
4. 将可能失败的 transport plan、task/owner 准备尽量前置，新 task 以未接纳请求的状态准备；提交后才开放新请求，随后让旧 owner drain。具体 task 注册失败路径必须有测试。
5. 能补偿的应用失败恢复旧活动对象且不改正式文件；无法完整补偿时记录实际活动状态并阻止后续变更，不能返回“旧态完整保留”的假保证。
6. 更新内存预算等操作不保证可恢复所有已淘汰缓存，但业务配置/owner 状态必须一致；缓存可冷化，不得用“原子”承诺撤销所有外部副作用。
7. 普通配置变更不注销全部管理员会话；首用户 setup 与明确认证配置变化保持单独的认证发布语义，并纳入同一配置写入仲裁。

### 3.2 持久化失败和崩溃

推荐保留已成功应用的新运行配置，显示“已应用，文件未同步”，提供“重试同步”；不为一次磁盘失败自动把 DNS 切回旧配置。存在未解决持久化状态时暂阻止后续配置变更，DNS 查询继续服务，减少叠加事务。

运行应用后、每次正式文件替换前仍需复核文件身份和所确认 fingerprint。此时发现外部新修改，保留已应用运行态并报告文件冲突，不能直接覆盖；用户重新查看并确认后才可重试同步。派生副本的观测状态也参与受管目标校验，不能只监测源路径却无条件覆盖副本。

| 失败位置 | 要求 |
| --- | --- |
| 校验/prepare/临时文件准备失败 | 不应用、不改正式文件，保留表单草稿 |
| runtime 或文件版本冲突 | 不盲目覆盖；回读状态重新确认，prepared 候选释放 |
| 运行时应用失败 | 不开始正式文件提交，回报真实补偿结果 |
| 应用成功但 journal 决策/文件提交失败 | 标记 applied-unpersisted，显示对应版本；重试只持久化现有活动源，不重复应用 |
| 源已替换、派生副本未替换 | 保留 COMMIT_DECIDED journal，恢复只补齐已验证目标 |
| 请求超时/响应丢失 | 返回/回读 operation_id、状态和 revision；禁止自动重做新增/改名 |

持久化状态机至少区分 PREPARED 和 COMMIT_DECIDED。启动恢复不能对任何临时候选都调用现有 roll-forward：

- 只有 PREPARED、没有持久化的应用后决策时，保留最近完成持久化的配置，丢弃该未提交候选；进程内刚生效但未落盘的变化可能在崩溃后丢失，界面必须明确这一风险。
- COMMIT_DECIDED 已持久化且目标均为已知旧/新 fingerprint 时，先补齐同一候选文件，再按新配置启动；不把旧进程的运行状态当作新进程已经应用。
- journal 损坏、路径身份不符或存在未知外部内容时不擅自覆盖，报告人工处理要求；不能在正常运行期间借恢复自动加载未确认外部文件。
- source 与派生副本的替换不是跨文件原子事务；Windows 每个 crash point 单独验证，Unix 特有实现记录未实测。

临时文件、journal 和内部活动源含敏感配置，权限不得放宽；不写入 Git，不通过状态 API 返回正文或 Secret 实际值。

## 4. 外部文件变更

### 4.1 检测与提示

复用现有轮询机制，不要求新增文件监听依赖。轮询在后台有界读取，区别内容变化、缺失、不可读、超限及仅元数据变化；两次稳定采样用于去抖，不作为锁或安全 CAS。

自写识别必须匹配完整提交的 fingerprint/operation，不能用“忽略下一次事件”跳过真正外部修改。新状态通过配置状态 GET 提供，页面可轮询；WS 就绪后可推送失效通知，但不能依赖解析记录自动刷新开关。

外部改动绝不自动 reload，也不自动变更会话或覆盖编辑草稿。Hosts/规则集资源文件原有自动刷新属于另一条资源链路，不随本次主配置 watcher 改造一起禁用。

### 4.2 处理动作

| 动作 | 行为 |
| --- | --- |
| 查看差异 | 比较当前活动源与当前磁盘源；只返回有界、脱敏、类型化字段差异 |
| 还原文件 | 确认后按活动源覆盖受管文件，运行时不重载；要求 active/file 两个版本匹配 |
| 修改并采用 | 将选中的可写模块差异载入对应表单，允许调整后组成候选；通过相同热更新流程 |
| 普通表单保存 | 从活动源修改；有外部差异时明确确认丢弃未采用内容，再写回新活动源 |
| 取消处理 | 保持运行配置和外部文件不变，提示继续保留 |

外部一次修改多个依赖资源时，可在一个“配置变化处理”工作区中组合多个模块草稿，按完整引用图一次校验/应用；不要求先保存带悬空引用的中间状态，也不开放任意 YAML/JSON Patch。改名必须指定旧名到新名的映射，不能仅凭删除/新增条目猜测引用关系。

外部文件语法无效时显示受限解析错误，只能还原或由用户在文件端修正，不把无效正文自动载入表单。只读启动字段混入差异时阻止整体采用；允许只选择可写部分，明确其他变化将被还原。认证 hash/Secret 值差异仅显示受保护字段发生变化。

预览后文件再次改变，返回新的冲突而不是继续覆盖。非合作外部编辑器不遵守进程锁，普通 filesystem replace 无法提供严格跨进程 compare-and-swap；提交前内容核对、精确目标校验和提交后复读可检测多数冲突，但不宣称彻底消除核对与替换之间的竞争窗口。UI 应提示在确认保存期间避免同时使用外部编辑器。

## 5. 热更新范围

| 变更 | 实施目标与边界 |
| --- | --- |
| 名称和引用 | 同命名空间唯一；旧名定位、整张类型引用图更新，活动快照整体发布 |
| 策略、上游、资源配置、客户端匹配/覆盖、TTL/ECS | 候选准备后切换；旧请求使用旧快照完成，不重算历史 |
| listener 路由/策略及可复用绑定 | 按物理 endpoint 复用未变 socket，只预绑定新增 socket；逻辑改名不触发同端口重复 bind |
| listener 协议/地址变化 | 新入口准备好再接纳，旧连接按 deadline drain；排他端口无法无中断替换时拒绝候选并解释，不自动停服务 |
| 内存预算 | 调整共享预算；避免无关重建所有池，纯改名不改变答案语义 |
| 快照设置 | owner/generation 串行切换，周期在下一任务边界读取，不重新预热活动缓存 |
| R/G/T | 活动策略立即更新，正在执行任务用冻结版本；下一清理任务采用新版本 |
| 详情 enable | owner 始终可管理，开关影响新事件接纳，关闭时有界排空；历史读取/统计/保留继续 |
| logs enable/level/path | 预开新输出，更新已有 filter/layer/输出 owner；切换失败保留旧输出，off -> on 不依赖启动时曾开启日志 |
| database/webui/work | 本期 API 和外部采用均只读；目录/存储位置和 Management 自身绑定是启动级变更，不为本期增加在线搬库/自迁移 |

不停机指进程和未受影响的 DNS 服务持续可用，不等于任意协议变化都能让所有长连接永久不重连。未满足热更新条件的变更在应用前拒绝，不退回“先保存、等重启”的默认交互。

## 7. 阶段性提交与验收

专项不另建一套提交编号，使用子计划中的检查点：

- BC-02：活动源表达和配置版本基础（CR-01）。
- BC-03：运行时应用及差量 listener 准备（CR-02）。
- BC-29：应用后持久化/journal 恢复（CR-03）。
- BC-30：外部文件只提示与处理接口（CR-04）。
- BC-31：日志热 owner（CR-05）；详情/缓存/保留 owner 随 BC-07/08/21 完成。
- FC-02：表单和应用/同步状态基础；FC-16：外部差异工作区及真实接口。
- BC-32：配置专项故障回归（CR-06）；不能把各实现提交应有的测试全部延后至此。

Windows 本机必须覆盖：正常保存持续请求、名称和引用整批变化、修改一项 listener 不重绑未变入口、外部改文件但 DNS 不变化、无效/删除/重复外改、还原、组合采用、普通保存丢弃差异确认、日志关开/换路径、磁盘写失败、双文件各 crash point、HTTP 丢失、旧请求 drain、并发资源刷新与配置写入。

配套核心耗时验收遵循 D-11。Linux 特有代码进行源码审查，未运行的测试标为未验证，不作为本轮阻塞项。P0 只沉淀已验证的内部契约；本专项运行流程必须在真实接线和上述测试通过后再记录为正式实现，不能借 DTO 测试提前标记通过。
