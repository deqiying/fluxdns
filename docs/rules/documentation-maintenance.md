# 文档维护规则

> 文档状态：有效
>
> 适用范围：仓库 Markdown、文档目录/索引、状态、源码依据与维护流程
>
> 维护入口：[文档总索引](../README.md) · [规则索引](README.md)

## 1. 目标与权威

文档必须可定位、职责单一、与代码同批维护，并能区分设计、事实和证据。源码、配置、schema 与实际命令证明当前行为；架构记录接受的设计；计划描述尚待改变或验收的内容；规则约束协作方式。

同一事实只在一个位置完整维护，其余入口给摘要和链接。权威文档清单以[总索引](../README.md)为准，尤其：

- 配置字段/默认值/路径/校验只在 [implementation/configuration.md](../implementation/configuration.md) 完整描述，并同步 model、resolve、validate 与示例。
- API 字段以 [OpenAPI](../../frontend/openapi/management-api-v1.yaml) 为准，生成的 TypeScript 不人工编辑，Markdown 不复制全套 schema。
- 工具来源、版本与安装/缓存规则放在 rules；产品构建、运行和发布脚本的实际步骤、产物与限制放在 [implementation/delivery.md](../implementation/delivery.md)。文档检查器由[项目文档维护技能](../../.agents/skills/project-doc-maintenance/SKILL.md)维护，支持范围以本规则为准。
- 根/前端 README 是最短使用入口；AGENTS 是强制路由；项目 skill 执行本规则，不复制状态枚举、完整目录树和第二套权威表。

实现与设计冲突时先确认预期契约，明确记录实际差距；不能按更新时间选边，也不能仅改文档掩盖代码缺陷。超出获准范围的产品修复单独评审。

## 2. 分类与目录

先按文档用途、再按代码领域组织：

```text
docs/
  README.md
  plans/                         # 活动变更与验收
    README.md
    <topic>.md
  architecture/                  # 已接受设计
    README.md
    system.md
    management.md
    frontend.md
    backend/
      README.md
      overview.md
      modules/
        README.md
        <module>.md
  implementation/                # 源码事实与验证边界
    README.md
    configuration.md
    delivery.md
    backend/
      README.md
      lifecycle.md
      dns-pipeline.md
      background-services.md
      management.md
    frontend/
      README.md
      application.md
      pages.md
  rules/                         # 协作与工程规则，不是 DNS 规则集
    README.md
    documentation-maintenance.md
    environment-usage.md
    local-testing.md
```

| 内容要回答的问题 | 归属 |
| --- | --- |
| 必须怎样协作、调用工具、组织或验证？ | rules |
| 相对当前系统要改变什么、怎样实施/验收？ | plans |
| 为什么这样设计、职责和不变量是什么？ | architecture |
| 代码怎样运行、是否接线、证据和限制是什么？ | implementation |
| 从哪里进入、最短命令是什么？ | 最近一级 README |
| 临时日志、个人配置和一次性输出？ | `_fluxdns/` 或任务记录，不进入长期文档 |

方案不限跨领域，单模块重要行为变化同样可以建 plan；简单修复不机械创建方案。架构模块保留独立设计价值，实现按实际链路组织，不自动为每个模块/源码文件生成配对文档。

新增目录必须有稳定且不重叠的职责、实际多文档集合和 README；不预建空目录，不按作者、日期、任务编号或版本堆叠目录。不建立 archive/history、备份或旧路径跳转副本，历史交由 Git。

目录和普通文件使用小写英文 kebab-case，入口固定 `README.md`；`AGENTS.md` 与 skill 的 `SKILL.md` 保持各自约定。长期技术文档不散落在源码目录，工程 README 和 schema/生成类型留在所属工程。

## 3. 维护信息

普通文档在一级标题后声明 `文档状态` 和 `适用范围`。文档状态只取“草案”“有效”“已废弃”；草案不覆盖有效契约，废弃文档说明替代入口与删除条件，不长期保留空壳。

目录索引与规则使用公共信息即可。skill 保留 YAML frontmatter，不套普通文档状态块。

### Plan

头部增加 `计划状态` 和 `代码基线`（源码 commit 或明确待核对）。生命周期为：

```text
待评审 -> 待实施 -> 实施中 -> 待验收 -> 已完成
                                   -> 已取消（经明确范围决策）
```

待评审的文档状态为草案，获批后转有效/待实施。代码已完成、缺要求的运行验收时进入待验收，不能退回“未实现”。索引同步计划状态。

正文回答问题/现状依据、目标与非目标、相对基线的变更设计、步骤、风险、验证与退出条件。已完成/已取消只是清理前终态，不是长期保留方案的状态。

方案执行完成后，必须在同一交付批次依次完成：

1. 将新增或改变的实际逻辑沉淀到 `docs/implementation/` 对应文档，说明当前入口、调用链、行为、限制与验证证据；优先更新已有文档，不把阶段步骤原样搬入实现说明。
2. 核对方案是否改变原有设计。若职责、依赖、契约、不变量或设计取舍发生变化，同步更新 `docs/architecture/` 对应设计文档；未改变设计则不机械重写。不能为掩盖实现缺陷反向修改设计。
3. 同步受影响的规则、索引和入站引用，确认长期逻辑不再只存在于方案中。纯文档治理或规则变更沉淀到其权威 rules/skill，不虚构产品实现或设计变化。
4. 删除已完成的方案文档及计划索引项，不以“仍有参考价值”为由保留，不归档、不留跳转副本；历史过程由 Git 追溯。

未完成的实施或必要验收继续由活动计划跟踪，不能提前删除。方案取消时只沉淀已实际发生的变更和仍有效的决策，不能将未实施内容写成当前事实；确认剩余范围已处置后删除方案及索引项。

### Architecture

头部增加 `最后评审`（日期或待核对）。正文回答设计结论、职责/依赖、核心不变量、关键流程/失败语义、取舍和实现入口。

不维护总体完成比例、实现状态或历史测试数量。设计中的验证章节是契约要求，不是通过记录。已接受但未落地的设计必须明确边界并链接活动 plan，不把设计当愿望清单。

纯移动/排版不刷新评审日期；局部边界评审写明范围，不冒充整篇重审。示意模型/逻辑顺序不假装与源码逐项相同。

### Implementation

头部增加 `最后核对` 和 `核对基线`，使用实际检查的源码 commit，不等待未来文档提交哈希。

正文至少包含入口/调用链、实际状态或数据流、能力边界、证据与已知限制。关键能力采用下表，符号名附近链接真实源码，不只使用易漂移的行号：

| 能力 | 代码实现 | 正式入口接线 | 验证证据 | 已知限制 |
| --- | --- | --- | --- | --- |
| 关键行为 | 源文件与符号，或明确未实现 | 调用处、启用条件，或未接入 | 静态/定向测试/运行，日期、环境、基线与结果 | 未覆盖的平台、故障或功能差距 |

函数存在、mock 通过、生产接线、目标环境验收是不同证据。只在回查受影响源码后更新核对日期；局部核验明确范围，继承但未核验的陈述保留原日期/来源与限制。缺少可追溯证据的历史结果写“原文报告，本轮未复核”，不能迁移为新通过记录。

## 4. 与变更一起维护

“实时维护”指有文档影响的代码变更在同一交付批次更新相应事实；合并/交付前说明未更新的原因。不靠定期改日期或自动摘要假装实时。

| 变更 | 必查与同步对象 |
| --- | --- |
| 功能、调用链、生命周期或失败行为 | 对应 implementation、源码与测试；契约变化再更新 architecture，活动计划更新剩余工作 |
| 仅内部重命名/重构 | 实现文档中的链接、符号与接线；不机械重写未改变的设计 |
| 配置字段/默认值/路径 | model/resolve/validate、示例、configuration；设计原则改变才同步 Config 设计 |
| Management API | OpenAPI、生成类型、handler/client、实现说明和契约测试；安全/依赖变化再评审架构 |
| 页面与查询状态 | 前端实现和对应源码/测试；分层/鉴权变化联动设计 |
| 工具或交付脚本 | manifest/脚本与 delivery；安装、缓存、调用规则变化联动 rules |
| 协作规则 | 对应 rules 与索引；强制路由/权限边界影响 AGENTS，skill 只调整必要导航 |
| 方案执行完成 | 新逻辑沉淀到对应 implementation；原有设计改变时同步对应 architecture；完成后删除方案、索引项并修正入站引用 |
| 文档移动/删除 | 最近索引、所有入站链接与源码引用；一级结构变化更新总索引/AGENTS/skill |

维护流程为：定位已有权威与入站引用 -> 判断更新/拆分/新增 -> 核对事实 -> 按段落职责编辑 -> 更新索引和相对链接 -> 验证 -> 收口计划。不能仅按文件名移动整份混合文档。

文本用 UTF-8 无 BOM 和 LF；命令注明执行目录、前置条件和副作用。未执行命令不能写为通过；不保存个人绝对路径、秘密、真实 token、内部地址或无必要的原始长日志。

## 5. 检查入口与边界

从仓库根目录执行：

```powershell
pwsh -File .agents/skills/project-doc-maintenance/scripts/check-docs.ps1
git diff --check
git status --short
```

技能内的 [`check-docs.ps1`](../../.agents/skills/project-doc-maintenance/scripts/check-docs.ps1) 只读检查 Git 跟踪及未忽略新增的 Markdown，排除已删除文件和被忽略产物，包含根/前端 README、AGENTS 和项目 skill。默认从脚本位置定位仓库根目录；`-RootPath` 可显式指定待检查仓库。它使用 PowerShell 7 自带 Markdig，不安装依赖、不请求网络、不改正文或日期、不触发 CI/发布。

支持 CommonMark 行内/引用式链接、图片、相对路径、目录、同页/跨页 Markdown 标题锚点、GitHub 风格重复标题 ID、百分号编码、代码块/行内代码排除、GFM pipe table 和 skill YAML frontmatter。外部 URL 只识别为外链，不做可用性断言。

检查编码/BOM/LF、单一 H1、标题跳级、fence 闭合、维护信息、分类目录/README 与本地链接。脚本不验证代码内行号片段、任意 HTML 链接/自定义 anchor、模板 URL 或额外 Markdown 扩展；遇到明确不支持的结构报错并要求改用受支持写法，或先扩展并验证检查器的支持范围，不能静默标为通过。表格内容对齐与文字含义仍需人工审查，解析成功不等于布局或语义正确。

检查器统一存放在该技能的 `scripts/`，不维护独立测试版本。检查器变更后重新执行仓库文档检查，并按改动核对相关语法、错误路径和只读边界。自动检查只能证明支持范围内结构正确，不判断代码是否真实实现或是否完成验收。

## 6. 交付与退出

人工收口必须确认：

1. 设计、事实、计划与规则没有重新混在同一段落；每个事实有唯一完整来源。
2. 新结构和索引一致，旧路径、空目录、备份和跳转副本已清理，源码链接与符号真实存在。
3. 日期/基线只覆盖实际核查范围，运行、静态、历史报告与未执行项明确区分。
4. 计划剩余实施与验收未丢失；已完成方案的新逻辑已沉淀到对应 implementation，受影响设计已同步到 architecture，方案文档及索引项已删除。
5. diff 没有产品代码、schema、版本或权限的未授权变化，保留用户无关工作树修改。

纯文档整理通常不需要重跑 Cargo/pnpm 全量测试；新增运行结论必须执行对应验证，检查脚本改动按上述边界验证。未明确授权不自动提交、push、部署、安装工具或增加 CI。
