# 文档维护规范

> 文档状态：有效
>
> 适用范围：FluxDNS 仓库内所有受 Git 跟踪的 Markdown 文档、配置示例中的说明性内容，以及文档目录和索引
>
> 维护入口：[文档总索引](../README.md) · [规范文档索引](README.md)

## 1. 目标

本规范用于保证文档可定位、可判定权威、可随实现演进并可安全废弃。文档维护必须满足以下结果：

- 读者能从索引找到正确文档，不依赖文件名猜测；
- 文档目录职责稳定，目录结构变化与索引、路由和引用同步维护；
- 同一事实只有一个完整权威来源，其他文档通过摘要和链接引用；
- “目标设计”“当前实现”和“后续计划”明确分开，不把计划描述成已交付能力；
- 行为、配置或流程变化与直接受影响的文档在同一变更中更新；
- 过期内容被修正、迁移或删除，不通过复制到归档目录继续保留多个版本。

## 2. 权威边界

### 2.1 权威来源

| 内容 | 权威来源 | 同步要求 |
| --- | --- | --- |
| 项目协作、工具和变更边界 | 根 [`AGENTS.md`](../../AGENTS.md) 与 `docs/standards/*.md` | 具体规范不得与 `AGENTS.md` 冲突；新增规范必须补齐路由 |
| 文档导航和目录职责 | [`docs/README.md`](../README.md) | 一级文档或目录变化时同步更新 |
| 后端总体架构和跨模块契约 | [`backend/architecture.md`](../backend/architecture.md) | 模块文档不得单独改变跨模块契约 |
| 后端模块内部设计和实现边界 | [`backend/modules/*.md`](../backend/modules/README.md) | 源码行为变化时更新对应模块文档 |
| 后端阶段、总体进度和验收门槛 | [`backend/development-plan.md`](../backend/development-plan.md) | 只记录里程碑级进度与证据摘要，不承载详细设计 |
| 配置字段、路径、校验和迁移 | [`backend/configuration-reference.md`](../backend/configuration-reference.md) | 必须与 `config-example.yaml`、配置模型、校验和测试同步 |
| 前端总体架构和实施边界 | [`frontend/architecture.md`](../frontend/architecture.md) | 前端目录入口由 [`frontend/README.md`](../../frontend/README.md) 维护；项目工具链和命令调用由 [`standards/environment-usage.md`](environment-usage.md) 维护 |
| 面向使用者的项目概览和入口 | 根 [`README.md`](../../README.md) | 只保留高层摘要，详细内容链接到 `docs/` 权威文档 |

源码、测试、schema 和实际命令结果是“当前实现是否如此”的验证依据；文档是项目接受的设计、契约和维护入口。两者冲突时不得按更新时间直接选择一方，也不得只修改其中一边：应先确认预期契约，再在同一任务中对齐实现、测试、示例和权威文档，或明确记录尚未实现的边界。

### 2.2 单一事实来源

同一事实只在一个权威文档中完整展开。例如：

- 配置字段的默认值和校验规则只在 `backend/configuration-reference.md` 完整定义；架构与模块文档只说明使用方式并链接过去；
- 总体完成比例、当前阶段和下一步只在 `backend/development-plan.md` 维护；根 `README.md` 只保留面向读者的阶段摘要；
- 模块内部数据结构和失败语义在对应模块文档维护；跨模块依赖方向在 `backend/architecture.md` 维护。

发现重复内容时，保留权威文档中的完整版本，将其他位置收敛为必要摘要和相对链接。不得通过复制整段内容解决“入口不明显”的问题，应补索引或链接。

## 3. 文档目录结构与选址

### 3.1 基准结构

仓库文档采用以下基准结构：

```text
README.md                         # 面向使用者的项目概览与文档入口
AGENTS.md                         # 项目级协作规则和强制文档路由
frontend/README.md                # 前端工程入口
docs/
├── README.md                     # 文档总索引与一级领域路由
├── backend/
│   ├── README.md                 # 后端文档索引
│   ├── architecture.md           # 后端总体架构与跨模块契约
│   ├── development-plan.md       # 后端阶段、进度与验收
│   ├── configuration-reference.md # 配置公共契约
│   └── modules/
│       ├── README.md             # 后端模块文档索引
│       └── <module>.md           # 与源码职责对应的模块文档
├── frontend/
│   ├── README.md                 # 前端文档索引
│   └── architecture.md           # 前端总体架构与实施边界
├── standards/
│   ├── README.md                 # 跨模块规范索引
│   └── <standard>.md             # 可执行的开发、协作或验证规范
└── plans/                        # 可选；仅存放需要仓库内评审的未实施方案
    ├── README.md                 # 方案索引、状态和退出条件
    └── <topic>.md
```

`docs/plans/` 是按需创建的可选目录，当前没有方案时不创建空目录。除根 `README.md`、`AGENTS.md` 和代码主目录自己的 `README.md` 外，长期技术文档统一放入 `docs/`，不得散落到源码目录或仓库根目录。

一级目录职责必须互斥且稳定。`backend/`、`frontend/` 按代码领域组织长期技术文档，`standards/` 存放跨领域规范，`plans/` 仅存放需要仓库内评审的跨领域未实施方案。仅当新目录对应稳定代码领域，或现有权威文档无法承载且同类文档已经形成明确集合时，才新增一级子目录；普通单一主题默认更新现有权威文档，不为一个文件创建主题目录。不得按作者、日期、任务编号或版本建立长期目录层级，也不得预建空目录等待未来内容。

### 3.2 文档选址

新增文档前按以下顺序判断位置：

1. 跨模块且可执行的协作、开发或验证规则放入 `docs/standards/`。
2. 配置公共契约直接更新 `docs/backend/configuration-reference.md`，不为单个配置块另建平行参考文档。
3. 后端跨模块架构直接更新 `docs/backend/architecture.md`；单模块设计放入 `docs/backend/modules/`。
4. 后端阶段、进度、后续任务或总体验收更新 `docs/backend/development-plan.md`。
5. 前端跨模块方案更新 `docs/frontend/architecture.md`；仅与前端工程使用相关的入口和命令更新 `frontend/README.md`。
6. 无法形成长期维护价值的调查记录、命令原始输出、一次性检查清单和个人笔记不进入 `docs/`。本地测试产物按[本地测试规范](local-testing.md)放入 `_fluxdns/`，任务证据可保留在提交或评审记录中。

确需在仓库中评审尚未实施的独立技术方案时，可以在首次需要时创建 `docs/plans/`，并同时创建该目录的 `README.md`。方案必须写明实现状态和退出条件；实施完成后，将长期有效的契约迁入对应权威文档，再删除已无独立价值的方案。不得为保存旧副本而创建 `archive/`、`history/` 或按日期堆叠的归档目录；Git 历史承担版本追溯职责。确有审计或发布留档要求时，应另行定义专用产物和保留策略。

### 3.3 目录结构变更

新增、移动、重命名或删除文档目录时必须在同一变更中完成以下事项：

1. 说明新旧目录职责，确认不会与现有一级目录或权威文档重叠。
2. 更新 `docs/README.md` 的目录树、快速路由和职责说明；涉及协作必读入口时同步更新根 `AGENTS.md`。
3. 为新增的多文档目录创建 `README.md`；目录删除前先迁移仍然有效的信息，并删除或改写所有入站链接。
4. 使用 `rg` 检查路径、文件名和标题引用；确认代码、配置、README、规范及模块文档中没有遗留旧路径。
5. 删除失去职责的空目录，不保留占位文件、旧目录副本或仅用于跳转的重复文档。

目录内文件增删只需更新最近一级索引；只有一级路由、目录职责或强制读取路径变化时，才同步修改 `docs/README.md`、本节基准结构或根 `AGENTS.md`，避免无内容变化的机械联动。

## 4. 命名与索引

### 4.1 命名

- 目录名和普通 Markdown 文件名使用小写英文 `kebab-case`；目录入口固定命名为 `README.md`。
- 模块文档名与源码模块名保持一致，例如 `dns-core.md`、`observability.md`。
- 文件名不附加 `final`、`new`、`latest`、作者名或日期来区分版本；版本变化通过 Git 历史和文档状态表达。
- 标题和正文默认使用简体中文；代码、命令、路径、配置键、API、库名和其他技术标识保留原文。
- 文本文件使用 UTF-8 无 BOM 和 LF。

### 4.2 索引

- `docs/README.md` 是文档总入口，维护一级文档与子目录的权威路由。
- 含多个长期文档的一级子目录必须提供 `README.md`，列出文档、职责和上位权威。
- 新增、重命名、移动或删除文档时，必须在同一变更中更新对应目录索引和所有入站链接。
- 新增规范文档时，还必须更新 `docs/standards/README.md` 和根 `AGENTS.md` 的文档路由。
- 新增后端模块文档时，还必须更新 `docs/backend/modules/README.md` 和后端架构中的模块映射。

## 5. 状态与内容格式

### 5.1 维护信息

受本规范维护的文档必须在一级标题后提供最小维护信息。设计、契约或计划涉及实现进度时，还必须提供“实现状态”和“最后核对”：

```markdown
# 文档标题

> 文档状态：草案
>
> 实现状态：未实现
>
> 适用范围：本文负责描述的唯一范围
>
> 最后核对：YYYY-MM-DD 或 待核对
>
> 关联文档：[上位文档](relative-path.md)
```

维护信息遵循以下规则：

- `文档状态` 只使用“草案”“有效”“已废弃”。草案可供评审，但不能覆盖已有有效契约；已废弃文档必须指向替代文档或写明删除条件。
- `实现状态` 只使用“未实现”“部分实现”“已实现”，并用正文说明边界；不得在状态行堆叠提交历史、测试数量或功能清单。
- `适用范围` 必填，用一句话说明文档负责和不负责的边界。
- `最后核对` 表示最近一次对照源码、配置、schema 或实际流程完成事实核验的日期。统一格式但尚未完成事实核验时必须写“待核对”，不得把格式迁移日期冒充核对日期；仅修正错字或排版时不更新。
- 索引、纯流程规范和不描述实现状态的说明文档可以省略 `实现状态` 与 `最后核对`。
- 受本规范维护的现有文档与新文档使用同一格式，不得继续使用含义混合的 `状态`、`日期` 或 `更新日期` 字段代替上述维护信息。

### 5.2 内容要求

- 开头先给结论、适用范围和关键边界，再展开设计、操作或证据。
- 当前行为、目标设计和后续计划必须使用独立段落或明确标签，不使用模糊的“已支持”“完整”“最新”。
- 关键行为说明应引用对应源码路径、配置项、测试范围或上位契约，但不粘贴会快速过期的大段实现代码。
- 命令示例必须说明执行目录、前置条件和适用范围。实际未运行的命令只能标为建议命令，不得描述为已通过。
- 验证证据保留结论、关键命令和必要边界，不持续累积完整日志、每个测试名或逐提交流水账。
- 使用仓库内相对链接，不写个人机器绝对路径；不得记录凭据、SecretRef 实际值、内部地址或不必要的私有数据。
- 外部资料应链接到原始或官方来源，并在版本可能变化时注明核对日期或适用版本。

## 6. 变更同步矩阵

修改实现或契约时，至少按下表检查直接受影响的文档：

| 变更类型 | 必查文档 | 条件性同步 |
| --- | --- | --- |
| 配置字段、默认值、路径、校验或迁移 | `backend/configuration-reference.md`、`config-example.yaml`、Config 模块文档 | 影响跨模块装配时更新后端架构；形成里程碑时更新开发计划 |
| 跨模块依赖、请求管线或生命周期 | `backend/architecture.md` 与受影响模块文档 | 形成里程碑或改变验收门槛时更新开发计划和根 README 摘要 |
| 单一后端模块行为、失败语义或模块测试 | 对应 `backend/modules/*.md` | 改变公共配置或跨模块契约时更新对应权威文档 |
| 阶段完成、优先级或总体进度 | `backend/development-plan.md` | 只有面向使用者的项目状态发生明显变化时更新根 README |
| 前端技术栈、边界或 Management API 设计 | `frontend/architecture.md` | 工程命令或目录变化时更新 `frontend/README.md`；后端契约变化时更新后端架构或对应模块文档 |
| 项目工具链、构建物、依赖目录、缓存或安装边界 | `standards/environment-usage.md` | 更新 `AGENTS.md` 中的强制入口或高层规则 |
| 本地测试目录、测试方法或结果记录要求 | `standards/local-testing.md` | 更新 `AGENTS.md` 中的强制入口或高层规则 |
| 新增或修改跨模块规范 | 对应 `standards/*.md`、`standards/README.md`、根 `AGENTS.md` | 影响文档导航时更新 `docs/README.md` 和相关模块入口 |
| 文档新增、移动、重命名或删除 | 所在目录 `README.md`、全部入站链接 | 改变一级路由或目录职责时更新 `docs/README.md`；改变协作读取路径时更新根 `AGENTS.md` |

纯内部重构、错字修正或排版调整若不改变行为和契约，可以不更新其他文档，但仍需检查是否暴露了已有文档错误。

## 7. 维护流程

### 7.1 新增或修改前

1. 从 `docs/README.md` 确认权威文档和目录职责。
2. 使用 `rg` 查找同一主题、配置键、模块名及现有入站链接，避免创建重复文档。
3. 对照源码、配置、schema、测试或实际命令确认事实，并区分已验证事实、目标设计和未验证边界。
4. 根据第 6 节确定必须同改的文档；不能在当前任务内对齐的实质冲突应先报告，不得静默保留。

### 7.2 修改时

- 使用满足目标的最小改动，不为统一格式批量重写无关文档。
- 行为与文档在同一变更中更新，避免先合并实现、以后再补文档。
- 修改标题或锚点前先搜索引用；移动文件时同步修正相对链接。
- 总结性文档只更新摘要和入口，详细事实留在其权威文档。
- 变更计划已实施完成时，将长期有效信息收敛到架构、配置、模块或规范文档，并更新总体进度；不再需要的临时方案应删除。

### 7.3 废弃或删除

1. 先确认内容是否仍包含唯一且长期有效的信息；如有，迁移到新的权威文档。
2. 使用 `rg` 查找并更新所有入站链接、文件名和标题引用。
3. 读者确实需要迁移窗口时，将文档标为“已废弃”并链接替代文档；否则可在同一变更中直接删除。
4. 删除后更新 `docs/README.md`、所在目录索引、根 README 和 `AGENTS.md` 中受影响的入口。
5. 不保留 `old-*`、`*-backup` 或归档副本；需要追溯时使用 Git 历史。

## 8. 验证与交付

文档变更至少执行以下检查：

1. 审查真实 diff，确认没有无关改写、重复权威或把计划写成已实现。
2. 检查实际目录与 `docs/README.md`、第 3.1 节基准结构一致；新增的多文档目录具备 `README.md`，且没有无职责的空目录或重复目录。
3. 检查新增和修改的仓库内相对链接目标存在；重命名或删除时用 `rg` 确认没有遗留引用。
4. 检查标题层级、表格、代码块、列表和维护信息可正常阅读。
5. 检查文本为 UTF-8 无 BOM、LF，且没有个人绝对路径、凭据或本地产物。
6. 执行 `git diff --check` 和 `git status --short`。

文档中的命令、配置示例、schema 或接口发生变化时，还必须执行与风险相称的定向验证；环境不具备时明确记录未执行项和原因。纯文档导航、措辞或流程规范变更默认不要求运行后端或前端测试，但不能把未运行测试写成通过。

## 9. 评审清单

- [ ] 实际目录结构符合基准，文档位置符合目录职责，索引和路由已同步。
- [ ] 适用范围、文档状态和实现状态清楚。
- [ ] `最后核对` 日期或“待核对”与实际核验范围一致。
- [ ] 当前实现、目标设计和后续计划已经区分。
- [ ] 每项完整事实只有一个权威来源，其他位置使用摘要和链接。
- [ ] 代码、配置、schema、示例和直接受影响的文档保持一致。
- [ ] 命令与验证结论可追溯，未执行边界已明确。
- [ ] 相对链接有效，未遗留重命名或删除引用。
- [ ] 不包含敏感信息、个人绝对路径、原始长日志或无维护价值的临时内容。
