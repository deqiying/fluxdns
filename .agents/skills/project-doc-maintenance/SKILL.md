# FluxDNS 文档维护技能

## 适用范围

当任务涉及 FluxDNS 的 Markdown 文档、文档索引、目录结构、文档状态、文档迁移/重命名/废弃、实现与文档对齐或文档链接校验时使用本技能。它只治理项目文档，不授权无关代码重构、工具安装、发布或推送。

## 必读入口与事实边界

开始修改前按以下顺序读取：

1. 根目录 `AGENTS.md`，确认项目协作基线和强制路由。
2. `docs/README.md`，确认一级目录职责和文档总入口。
3. `docs/standards/documentation-maintenance.md`，确认完整规范、维护信息格式和验证清单。
4. 与任务直接相关的权威文档：
   - 跨领域规范：`docs/standards/README.md` 及对应规范；
   - 后端：`docs/backend/README.md`、`architecture.md`、`configuration-reference.md` 或 `modules/<module>.md`；
   - 前端：`docs/frontend/README.md`、`docs/frontend/architecture.md`，以及工程入口 `frontend/README.md`；
   - 本地测试、工具链和构建物：`docs/standards/local-testing.md`、`environment-usage.md`。

源码、测试、配置、schema 和实际命令输出用于核对“当前实现是否如此”；文档用于表达项目接受的设计、契约和维护入口。发现实现、测试和文档冲突时，先确认预期契约并记录未决边界，不得按更新时间猜测，也不得只改文档掩盖实现问题。

## 核心决策链

维护任务沿着这条链路推进：

```text
识别主题与变更类型
  -> 搜索现有权威和入站引用
  -> 选择唯一维护位置
  -> 核对事实并标注实现边界
  -> 做最小内容修改
  -> 同步索引、路由和相对链接
  -> 执行结构、格式和针对性验证
  -> 交付变更范围与未验证项
```

### 1. 先判断是更新、拆分还是新增

- 使用 `rg` 搜索主题词、配置键、模块名、标题和旧路径；先找已有权威文档及所有入站链接。
- 已有文档能够完整承载该事实时，直接更新它；不要为了入口不明显而复制一份。
- 只有在内容对应稳定且互斥的职责、现有权威文档无法承载，或已形成明确的多文档集合时才新增文件/目录。
- 普通单一主题不创建主题目录；不按作者、日期、任务编号或版本堆叠目录。
- 一项事实只能有一个完整权威来源。其他文档保留必要摘要，并链接到权威来源。

### 2. 按职责选择位置

| 内容 | 维护位置 | 典型联动 |
| --- | --- | --- |
| 文档总导航、一级目录职责 | `docs/README.md` | 一级路由变化时检查 `AGENTS.md` |
| 跨模块、可执行的开发/协作/验证规则 | `docs/standards/<standard>.md` | 更新 `docs/standards/README.md` 和 `AGENTS.md` 路由 |
| 后端跨模块架构与契约 | `docs/backend/architecture.md` | 联动受影响模块文档 |
| 后端配置公共契约 | `docs/backend/configuration-reference.md` | 联动 `config-example.yaml`、配置模型、校验和测试说明 |
| 单一后端模块实现边界 | `docs/backend/modules/<module>.md` | 新增模块时更新 `modules/README.md` 和架构映射 |
| 前端总体架构或实施边界 | `docs/frontend/architecture.md` | 工程命令/目录变化时联动 `frontend/README.md` |
| 前端工程入口、命令和目录说明 | `frontend/README.md` | 仅在入口或工程约定变化时联动相关索引 |
| 一次性调查、原始日志、个人笔记 | 不进入长期文档 | 本地运行资料按 `local-testing.md` 放入 `_fluxdns/` |

`docs/plans/` 仅在确需仓库内评审未实施的独立方案时按需创建，并同时创建索引；实施完成后把长期有效内容迁入对应权威文档，删除无独立价值的方案。不要创建 `archive/`、`history/` 或备份副本，版本追溯交给 Git。

### 3. 核对维护信息和内容状态

文档一级标题后放置维护信息。`适用范围` 必填；描述实现的设计、契约或计划文档还必须包含 `实现状态` 和 `最后核对`：

```markdown
# 文档标题

> 文档状态：有效
>
> 实现状态：部分实现
>
> 适用范围：本文负责描述的唯一范围
>
> 最后核对：YYYY-MM-DD 或 待核对
```

- `文档状态` 只能是“草案”“有效”“已废弃”。草案不能覆盖已有有效契约；已废弃文档应指向替代文档或写明删除条件。
- `实现状态` 只能是“未实现”“部分实现”“已实现”，正文必须说明边界。目标设计、当前实现和后续计划使用独立章节或明确标签。
- `最后核对` 只有在对照源码、配置、schema 或实际流程完成事实核验后才填写日期；仅做格式迁移、错字或排版修正时保留原值，无法核验时写“待核对”。
- 不把提交历史、测试数量或功能清单塞进状态行，也不把“计划存在”写成“已实现”。

### 4. 根据变更类型同步文档

- 行为、配置、接口或失败语义变化：在同一变更中更新实现、示例、测试说明和直接受影响的权威文档；跨模块影响再更新架构/模块文档。
- 新增、移动、重命名或删除文档：同步最近一级 `README.md`、`docs/README.md`（若一级路由或职责变化）、`AGENTS.md`（若强制读取路径变化）及全部入站链接。
- 目录新增前说明新旧职责不重叠；包含多个长期文档的目录必须有 `README.md`。删除目录前先迁移仍有效的信息，并清理空目录、旧路径和重复副本。
- 仅修改目录内正文或措辞时，只更新必要的最近一级索引；不要无内容变化地机械修改全局入口。
- 方案已经实施时，将稳定契约收敛到架构、配置、模块或规范文档；临时方案没有独立价值就删除，而不是继续保留“历史版本”。

## 执行与验证逻辑

### 修改前

- 先用 `rg` 定位权威来源、重复事实、旧文件名和入站链接。
- 对照实际源码/配置/schema/测试，明确哪些是已验证事实、合理推断、目标设计和未验证边界。
- 根据变更类型列出必须联动的文档；无法在本次任务内解决的实质冲突先报告，不静默留下互相矛盾的描述。

### 修改中

- 只做满足目标的最小改动，保持现有标题、命名和相对链接风格。
- 目录和普通 Markdown 文件名使用小写英文 `kebab-case`，目录入口固定为 `README.md`；文本使用 UTF-8 无 BOM 和 LF。
- 命令示例写明执行目录、前置条件和适用范围。未执行的命令只能标记为建议，不能写成已通过。
- 不记录个人绝对路径、凭据、Secret 实际值、内部地址、不必要的原始长日志或本地产物。

### 修改后

至少完成以下检查，并根据风险追加定向验证：

1. 审查真实 diff，确认没有无关重写、重复权威或状态误标。
2. 检查实际目录树与 `docs/README.md` 及规范中的基准结构一致；多文档目录有 `README.md`，没有无职责空目录。
3. 用 `rg` 检查新增、移动、重命名或删除后的旧路径、标题和文件名引用；确认仓库内相对链接目标存在。
4. 检查维护信息、标题层级、表格、代码块、列表和文件编码/换行格式。
5. 执行 `git diff --check` 与 `git status --short`；提交时只暂存当前任务路径，保留用户无关的工作树修改。
6. 文档导航、措辞或流程规范的纯文档变更通常不要求运行后端/前端测试；若命令、配置、schema 或接口发生变化，执行相称的定向验证，并明确未执行项和原因。

## 交付要求

交付时说明：

- 修改、新增、移动、废弃或删除了哪些文档和目录；
- 每个主题的唯一权威来源及同步过的索引/引用；
- 已核验的事实、仍待核对的边界和实际执行的检查；
- 是否保留了工作树中的无关变更，以及未执行的测试或外部操作。

除非用户另行授权，不因文档任务自动提交、推送、删除历史资料或安装工具。
